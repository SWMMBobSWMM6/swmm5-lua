# swmm5-lua

EPA SWMM 5.2.4 in Lua, written by a translator that reads EPA's C, and judged against EPA itself: the binary `.out`
file byte for byte, and the `.rpt` report line for line except the three lines that print the wall clock.

**Result: 480 of 480 models identical**, twice: the first full gate (lua_1a, lua_1b, lua_1c, lua_1g, 9 November
2026) and an independent rerun from a clean checkout with the engine and the math regenerated (lua_v_a, lua_v_b,
lua_v_c, lua_v_g, the same day): every `.out` byte-identical, every `.rpt` identical except the three clock lines,
exit code 0 on every model, as EPA's. The 480 took 6,807 seconds of engine time in the first gate and 6,783 s in the
rerun, one at a time; the longest, EPA/72_H&H_Elements(2).inp, took 1,318 s and 1,340 s, under the gate's
1,800-second limit for one model. No model timed out.

It is not a new engine and not a wrapper: there is no C in it and it calls no other port. Every number it writes
is EPA 5.2.4's, including the results of EPA's own defects wherever EPA's behaviour is defined
(`lessons/02-epa-defects-found.md`). Lua is one of the eight languages of the second wave of Bob Dickinson's Code
Rosetta Stone app.

## The parity contract

The same as the earlier ports' (see `go/` or the swmm5-go repository): EPA SWMM 5.2.4 built from the USEPA v5.2.4
tag with gcc 13.3 `-O2` on x86-64 Linux with glibc 2.39 (`ref/Makefile`), on a processor with FMA and AVX2; each
model run in its own folder; pass = `.out` byte-identical (when EPA writes one) and `.rpt` identical after removing
`Analysis begun on`, `Analysis ended on` and `Total elapsed time`, the exit code the same (EPA's command line always
exits 0). When an input error stops EPA before it writes results, the engine must not write a results file either.
Corpus: the 480 gate models of `gate/models_all.tsv` from SWMMBobSWMM6/1729-SWMM5-Models-2030.

## Run

Requires Python 3 with **lupa** (`pip install lupa`; tested with **lupa 2.8**, which embeds **Lua 5.4.8**, on
Python 3.13.18). Nothing to build.

```sh
lua/runswmm model.inp model.rpt model.out          # = python3 lua/runswmm.py ...
```

**The launcher is Python; the engine is Lua.** lupa is a Python extension module that contains the Lua 5.4
interpreter (PUC-Rio's C source, compiled into the module); this machine has no stand-alone Lua 5.4 interpreter, and
the brief named lupa. `lua/runswmm.py` (15 lines) does three things: it creates a Lua state with Python's builtins and
`eval` kept out of it, loads `lua/swmm5/main.lua`, and calls it with the command line and the current working
directory (Lua's standard library has no `getcwd`, and EPA's report prints absolute paths built from it). Nothing
else crosses between Python and Lua: every line of the engine, its C runtime and its math runs in Lua.

To regenerate the engine: `python3 tools/c2x/emit_lua.py lua/swmm5` from the repository root (needs
`pip install libclang==18.1.1` and the clang 18 headers at `/usr/lib/llvm-18/lib/clang/18/include`; about 30 s).
To regenerate the math: `lua/make_glibm.sh GIMPLE_DIR TABLES_JSON` (the outputs of `tools/libm/build_glibm.sh` and
`extract_tables.py`; the default is the build kept at `/home/claude/ext/glibm_build`).

## How it was made

`tools/c2x/front.py` parses EPA's C with libclang; `tools/c2x/emit_lua.py` subclasses the Java back end
(`emit_java.py`) for its analysis (the front end's pointer modes, names made unique per function) and writes
everything else itself. When the port disagreed with EPA, the fix went into the translator or the runtime, never into
the generated files. The mapping, in full in the emitter's header:

- **Numbers.** C's `int`, `long`, `char` and enums are Lua integers (64-bit); `unsigned int` is masked to 32 bits
  after each operation that can leave the range. A C double is a Lua float, and every conversion from int to double
  is written out (`x * 1.0`), so a double never holds a Lua integer (whose arithmetic would wrap instead of round).
  Lua's `//` and `%` floor where C truncates: C's integer division is `R.idiv`, `%` is `math.fmod` (C's `%` on two
  integers). Lua's `>>` is logical: a signed shift is a floor division. `(int)x` is `R.D2I` (x86's answer, INT_MIN,
  for NaN and out-of-range values). C's `float` is rounded after each float operation by `R.f32`, a
  `string.pack('f')` round trip, which is C's `(float)` cast.
- **Pointers.** `char*` is a `CPtr`, a table of signed bytes and an offset. A pointer to a record or an array is the
  table itself (arrays are 0-based tables). A scalar pointer is a pair of values, table and key, passed as two
  arguments: `&Node[j].newDepth` is `Node[j], "newDepth"`, `*p` is `p[p__k]`; a local whose address is taken lives in
  a one-element table.
- **Statements.** Lua has no `continue` and no `switch`: every loop body is a `do ... end` block followed by a
  `::continueN::` label, and a `switch` is a set of gotos to one label per case group (C's fall-through kept), found
  by a binary search on the case values when there are six or more. `return` must end a Lua block, so it is written
  `do return x end`. An assignment used as a value is hoisted before its statement (26 places in EPA).
- **Names.** Globals are fields of a table `G`, functions of `F`, record constructors of `T`, string literals `S[n]`;
  enum values and macros are chunk-level `local NAME <const> = value`, which Lua 5.4 compiles into the instructions
  (no register, no upvalue). Every chunk sets `local _ENV = R.strict`, so a name the translator failed to declare is
  a run-time error, not a silent Lua global. The emitter reports any function that comes near Lua's limit of 200
  locals; none does.
- **Speed without changing what is computed.** A function reads a global array, pointer or record into a local
  (`local G_Link = G.Link`) when it uses it twice or in a loop and no function it can reach by the call graph assigns
  it (`analyze_globals` in the emitter); `pow(x, c)` with a constant `c` other than 2 is written `x ^ c` (below);
  `R.D2I` does its work in VM instructions instead of calling `math.floor`; `strcspn`, `strtok` and `fgets` work on
  whole sets and lines; the generational garbage collector is used (10 to 15% faster on the models tried).

## The runtime and the math library

- **printf, strtod, sscanf** (`rt.lua`): glibc's printf is reached through Lua: the runtime parses each C format and
  hands every numeric conversion to Lua's `string.format`, which passes it to the C library's `snprintf`. strtod and
  sscanf find the extent of a number by glibc's rules (hexadecimal floats, `inf`, `nan(...)` with its payload) and
  convert the digits with `tonumber`, which calls the C library's `strtod`. A parsed format is cached only for a
  string literal: EPA also formats with a buffer it rewrites, and a cache keyed on that buffer printed the wrong error
  message (`lessons/39-a-format-cache-must-not-key-on-a-buffer.md`). Checked against glibc 2.39 by
  `lua/test/run_crtcheck.sh` (the 1,394,252 cases from `tools/crt/test/mkfmt.c` that the other runtimes replay):
  **0 differ**, `%#g` included (`lua/results/crtcheck_result.txt`).
- **Math.** lupa's Lua calls the C library for `math.exp`, `math.sin`, `math.cos`, `math.tan`, `math.asin`,
  `math.acos`, `math.sqrt`, `math.abs`, `math.log`, `math.log(x, 10)` (C's `log10`) and `x ^ y` (C's `pow`). The
  module imports these symbols without a version (`nm -D`, `lua/results/lupa_symbols.txt`), and they bind to
  glibc's oldest versions, as `math.log(-1)` shows (below):
  `exp@GLIBC_2.2.5`, `pow@GLIBC_2.2.5` and `log@GLIBC_2.2.5` are the SVID-compatible wrappers around the same
  routines EPA reaches through `exp@GLIBC_2.29`, `pow@GLIBC_2.29` and `log@GLIBC_2.29`, and the others are the very
  symbols EPA imports. The wrappers change only results that are zero, infinite or NaN, and the test below found one
  difference in those: `log` of a negative number is a NaN with the sign bit clear (0x7ff8000000000000) where EPA's
  has it set, so `R.log` returns EPA's for x < 0. Two calls Lua does not offer as C does are glibc's own code
  translated from GIMPLE by a new Lua back end of `tools/libm/gim2x.py` (`glibm.lua`): pow when the exponent is 2,
  because Lua's `x ^ 2` is `x * x` (glibc's `pow(x, 2)` differs from `x * x` in 12,953 of 20,000,000 arguments), and
  atan, because `math.atan(x)` is `atan2(x, 1)` (different in 539 of 20,000,000; `lua/results/pow2_atan2.txt`,
  `lessons/40-lua-power-is-not-always-pow.md`). Lua has no fused multiply-add, which glibc's FMA routines use;
  `glibm_rt.lua`'s `fma` is exact: the Boldo-Melquiond method when every operand is moderate, otherwise the exact sum
  in 24-bit limbs, rounded once. The translations follow the GIMPLE's own control flow with `goto` and labels;
  functions with more than 170 temporaries keep the least used in a table, under Lua's 200-local limit.
- Checked bit for bit, NaN signs and payloads included, by `lua/test/run_libm_tests.sh` (`test/libmcheck.lua`, in the
  Lua that lupa embeds), each function called as the engine calls it: 11,000,672 random arguments over SWMM's ranges
  plus special values (`tools/libm/test/mkvectors.c`) and 3,300,000 edge cases (`mkedge.c`) for exp, log, log10,
  pow, sin, cos, tan, asin, acos, atan and fma, every pow vector run a second time through the translated pow alone
  (1,700,272 more), and 8,000,360 cases (`lua/test/mkexact.c`, from the PHP port's) for sqrt, floor, ceil, fabs,
  negation and the runtime's `(float)`, `(int)` and `(long)` casts: **0 differ** (`lua/results/libm_tests.txt`).
- **The other back ends are unchanged.** Adding the Lua back end to `gim2x.py` was additions only:
  `lua/test/check_gim2x_regen.sh` regenerates the TypeScript, Java, Go, Kotlin, JavaScript and Groovy translations
  with the new `gim2x.py` and compares them byte for byte with the shipped files, and regenerates the Lua one: all
  identical (`lua/results/gim2x_regen.txt`).
- **Big arrays.** A Lua array element takes 16 bytes, where a C double takes 8 and a char 1.
  Hydrology/sewer_rdii_problem.inp allocates 3.38 GB of RDII rainfall history in C (`gate/rdii_memory.py`), which as
  dense Lua tables would need about 12 GB, more than this machine has. So an array of more than 100,000 elements that
  C allocates zeroed is a table that stores only what is written with a value other than zero; reading an element
  never written gives the zero, through the table's metatable. The model then runs with 1.5 GB resident.

## Speed

The gate's clock: the first full gate took 6,807 seconds of engine time for the 480 models (113 minutes), one at a
time, on a 2-core machine shared with other agents' runs; the longest were EPA/72_H&H_Elements(2).inp, 1,318 s,
Hydrology/SCANLON.inp, 863 s, and EPA/attenuation_DW_High_CE.inp, 269 s. Against the PHP port's stored gate times
(also from this machine, at other times, so a rough guide only) the total is 2.05 times PHP's, and the median ratio
2.11 (62 models PHP took 5 s or more on; range 1.61 to 2.97): Lua 5.4's interpreter against PHP's tracing JIT. Start-up
(Python, lupa and the 43,000 lines of Lua compiled; `lua/runswmm --version`) takes 0.14 s of wall time, 0.05 s of
CPU. Hydrology/sewer_rdii_problem.inp took 222 s with 1.5 GB resident (EPA: 3.11 GB). No interleaved benchmark
against EPA was run (lessons/07).

The speed work was done before the gate, with a sampling profiler (a Lua count hook) on the slow models, because a
first measurement put EPA/72_H&H_Elements(2).inp near 24 minutes, close to the gate's limit: the global locals, the
`<const>` constants, the binary switch dispatch and `x ^ c` in the translator, and `R.D2I`, the string functions and
the generational collector in the runtime (above). The translator changes took EPA/master_extran_with_storage.inp
from 4.3 to 3.4 s of CPU (medians of three interleaved runs), and the collector took 10 to 15% more off the models
tried. None of them changes what is computed, and the gate ran after all of them.

## What this does not show

- That SWMM is right: identical to EPA means EPA's answers, good or bad.
- Other platforms: the port calls the system libm through lupa's Lua, so on another machine it should follow EPA built
  there, apart from the two translated routines, which give EPA-on-x86-64 answers everywhere; only x86-64 Linux with
  glibc 2.39, lupa 2.8 and Lua 5.4.8 was run. A lupa built against a newer glibc would bind the newer symbol versions
  (and `R.log`'s correction would then be a no-op, not an error).
- A Lua other than the one in lupa: a stand-alone Lua 5.4, or one built with another number configuration
  (`LUA_FLOAT_TYPE`, `LUA_INT_TYPE`), would need the checks again.
- Paths no gate model exercises: streets and inlets (one deck, which stops on input errors), climate files, USE
  HOTSTART, USE INFLOWS, USE RUNOFF; the stepping API is translated but only the command line was gated.
- A checked run in C's sense: an out-of-range read of a Lua table gives `nil`, and arithmetic on it stops the run
  (except in the big zero-default arrays, where it gives the zero), but a C overrun that stays inside a table's
  written part would not show; the gate would see it only if it changed an output.
- No person has reviewed the generated code line by line; the evidence is the gate and the runtime checks.
